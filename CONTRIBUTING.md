# Contributing to DHRUVION

Thank you for your interest in contributing to DHRUVION! This document outlines the development workflow, coding standards, and contribution process.

## Development Workflow

### Prerequisites

- **Python 3.11+** (backend)
- **Node.js 20+** and **npm** (frontend)
- **Git**
- Optional: **QGIS** for inspecting planetary geospatial products
- Optional: **Ollama** or configured LLM endpoint for AI assistant

### Quick Start

```bash
# Backend
cd backend
python -m venv .venv
# Windows PowerShell:
.venv\Scripts\Activate.ps1
# macOS/Linux:
source .venv/bin/activate
pip install -r requirements.txt
uvicorn app.main:app --reload

# Frontend (in separate terminal)
cd frontend
npm install
npm run dev
```

The frontend will be available at `http://localhost:5173` and the backend API at `http://localhost:8000`.

### Environment Configuration

Copy the example environment files and adjust as needed:

```bash
# Backend
cp backend/.env.example backend/.env

# Frontend
cp frontend/.env.example frontend/.env
```

Required backend variables:
- `JWT_SECRET_KEY` - Secure random string (use `openssl rand -hex 32`)
- `DATABASE_URL` - SQLite path or PostgreSQL connection string
- `FRONTEND_ORIGIN` - Frontend URL for CORS

Required frontend variables:
- `VITE_API_BASE_URL` - Backend API URL (e.g., `http://localhost:8000/api`)

### Running Tests

```bash
# Backend tests
cd backend
python -m pytest tests/ -v

# Frontend type checking
cd frontend
npx tsc --noEmit

# Frontend linting
npm run lint

# Frontend production build
npm run build
```

## Code Style

### Frontend (TypeScript/React)

- **Formatting**: Follow the project's oxlint configuration
- **Types**: Strict TypeScript (`noUnusedLocals`, `noUnusedParameters`, `erasableSyntaxOnly`)
- **Components**: Functional components with hooks
- **State**: React Context for global state, localStorage for persistence
- **Styling**: Tailwind CSS with design system tokens from `tailwind.config.js`
- **Imports**: Use path aliases where configured

### Backend (Python/FastAPI)

- **Formatting**: Black (line length 88)
- **Types**: Full type hints with Pydantic models
- **Architecture**: API layer → Application services → Domain logic → Data adapters
- **Error handling**: Structured error responses with stable codes
- **Security**: Never log secrets, use environment variables for credentials

### Git Commit Messages

Use conventional commits format:
```
type(scope): description

[optional body]

[optional footer]
```

Types: `feat`, `fix`, `docs`, `style`, `refactor`, `test`, `chore`

Example:
```
feat(auth): add password strength indicator to signup form

- Added inline password requirements with color-coded status
- Integrated zxcvbn-inspired strength meter

Closes #42
```

## Pull Request Process

1. **Fork** the repository and create a feature branch
2. **Write tests** for new functionality
3. **Run all checks** locally (typecheck, lint, tests, build)
4. **Update documentation** for any user-facing changes
5. **Open a PR** with a clear description of changes
6. **Address review feedback** promptly
7. **Squash and merge** after approval

### PR Checklist

- [ ] All TypeScript compilation passes (`tsc --noEmit`)
- [ ] All lint warnings resolved or justified
- [ ] Backend tests pass (`pytest tests/ -v`)
- [ ] Frontend production build succeeds (`npm run build`)
- [ ] Documentation updated for user-facing changes
- [ ] No secrets or credentials in changes
- [ ] Large assets not committed (use Git LFS if needed)

## Architecture Guidelines

### Frontend

- **Components**: Keep components small and focused
- **Map rendering**: Use Leaflet with custom Mars CRS (`components/map/mars.ts`)
- **State management**: React Context for auth, localStorage for UI preferences
- **API client**: Typed endpoints in `services/api/endpoints.ts`
- **Design system**: Use Tailwind tokens from `tailwind.config.js`

### Backend

- **Layer separation**: API routes → Application services → Domain logic → Data adapters
- **Deterministic core**: All geospatial calculations in pure Python functions
- **Provenance**: Every data response includes source metadata and availability status
- **Error handling**: Return `UNVERIFIED` for missing data, never fabricate values

### Data Handling

- **Raw data**: Immutable, never modified, stored in `data/raw/` (excluded from Git)
- **Processed data**: Generated by scripts in `scripts/`, stored in `data/processed/`
- **Metadata**: Every layer has a manifest with source, CRS, resolution, units, warnings

## Feature Status Labels

All UI elements displaying data must use appropriate status badges:

- **OBSERVED** - Measured/recorded source data (green)
- **DERIVED** - Computed from observed layers (amber)
- **SIMULATED** - Scenario/decision-support output (cyan)
- **UNAVAILABLE** - Not connected or outside coverage (muted)

Never present simulated data as verified observations.

## Security

- **Never commit secrets** - API keys, tokens, passwords, JWT secrets
- **Use environment variables** for all credentials
- **JWT_SECRET_KEY** must be a secure random string in production
- **Database credentials** via `DATABASE_URL` environment variable
- **Report security issues** privately via GitHub security advisories
